# 第一周任务 1.2 & 1.3：消息主链路与概念地图 (`docs/week1-concepts.md`)

## 第一部分：任务 1.2 —— 先画一条消息怎么走

### 1. 业务场景
小明在自己的浏览器输入“你好”，点击发送后，小红、张三、李四在另一台电脑（或手机）的浏览器页面上实时看到“你好”。

### 3. 任务 1.2 必答问题解答

1. **为什么小明不能直接把消息显示到小红的页面上？**
   * **网络与寻址角度**：小红的浏览器只是一个运行在小红电脑上的客户端进程，没有固定公开监听的服务端口，小明的浏览器既不知道小红的 IP 和端口，也无法直接向另一个浏览器发起入站连接。
   * **浏览器安全沙箱角度**：现代浏览器遵循严格的安全隔离机制，网页里的 JavaScript 代码无权直接操作或注入另一台设备的内存与页面 DOM，必须通过双方都建立连接的**聊天服务器**作为中转枢纽。
2. **浏览器怎样找到服务器？**
   * 浏览器通过用户在地址栏输入的 URL（如 `http://192.168.1.100:8000`）找到服务器：其中 `192.168.1.100` 是服务器在当前局域网内的 **IP 地址**（定位到哪台电脑），`8000` 是 **端口号**（定位到这台电脑上的 FastAPI 聊天服务进程）。网页加载后，前端脚本使用 `window.location.host` 自动拼接出 `ws://192.168.1.100:8000/ws`，从而精准找到同一台服务器建立 WebSocket 连接。
3. **手机热点或路由器在这里做了什么？**
   * **组建局域网与分配地址（DHCP）**：为接入同一热点/路由器的每台电脑和手机分配唯一的局域网内部 IP 地址（如 `192.168.1.100`、`192.168.1.101`），使它们处于同一网段。
   * **数据包交换与路由转发**：当小明或小红的设备向 `192.168.1.100:8000` 发送 HTTP 或 WebSocket 数据包时，路由器/热点根据目标 IP 地址将数据包准确转发给服务器电脑，并将服务器的广播响应包转发回各台客户端设备。
4. **服务器需要知道有哪些浏览器已连接吗？为什么？**
   * **必须知道**。因为 WebSocket 广播的本质是“服务器收到某一个连接发来的消息后，主动向所有当前在线的连接逐个发送这份消息”。如果服务器不在内存中维护一份“当前已连接浏览器列表”（如 `active_connections` 列表），它收到小明的“你好”后，就只能回复给小明自己（变成单人“回声”），而无法把消息推送给小红、张三和李四。

## 第二部分：任务 1.3 —— 用 AI 建立“概念地图”

### 1. 本项目场景下的核心概念解释

| 核心概念 | 结合本聊天室项目的通俗解释 |
| :--- | :--- |
| **浏览器 (Browser)** | 用户用来打开聊天室网页的软件（如 Chrome、Edge、Safari），负责渲染 HTML 界面并执行前端 JavaScript 代码。 |
| **客户端 (Client)** | 发起连接、使用服务的一方。在本项目中，每个打开了聊天室页面的浏览器标签页就是一个客户端。 |
| **服务器 (Server)** | 运行 Python/FastAPI 后端程序、等待客户端连接并提供网页与消息转发服务的电脑或进程。 |
| **HTTP 协议** | “客户端问一句、服务器答一句”的无状态短连接协议。在本项目中，浏览器刚输入网址时用 HTTP `GET /` 请求把聊天室的 HTML 网页代码下载到本地。 |
| **WebSocket 协议** | 建立在单个 TCP 连接上的**全双工（双向）持久长连接协议**。网页加载完成后，通过 HTTP Upgrade 握手升级为 WebSocket（`ws://.../ws`）；只要不断开，客户端可以随时发消息，服务器也能随时主动把别人的消息推送给客户端。 |
| **IP 地址 (IP Address)** | 设备在网络中的唯一“门牌号”（如 `192.168.1.100`），告诉网络数据包应该送到哪一台电脑或手机。 |
| **端口 (Port)** | 一台电脑上的“具体房间窗口号”（范围 `0~65535`，本项目使用 `8000`）。IP 决定找到哪台电脑，端口决定把数据交给这台电脑上的 FastAPI 聊天程序，而不是微信或浏览器等其他软件。 |
| **`127.0.0.1`** | **本机回环地址（Loopback）**，等价于 `localhost`，永远指向“当前正在操作的那台设备自己”。数据不会经过外部网卡或路由器。 |
| **本机局域网 IP** | 路由器或手机热点分配给服务器电脑网卡的局域网地址（如 `192.168.1.100` 或 `172.20.10.2`），同一局域网内的其他设备必须用这个 IP 才能找到服务器。 |
| **`0.0.0.0`** | 服务器启动时指定的**全网卡监听绑定地址（通配地址）**。告诉操作系统：“无论是本机 `127.0.0.1` 发来的请求，还是从 Wi-Fi 局域网 IP 发来的请求，只要端口是 8000，我全都接收”。 |

### 2. 概念关系图

```text
+-------------------------------------------------------------------------+
| 客户端层：用户的手机 / 电脑                                              |
|  [浏览器 (Client)]                                                      |
|    │                                                                    |
|    ├─ 第一步：通过 HTTP 协议 (GET http://192.168.1.100:8000/)           |
|    │          ──► 获取聊天室 HTML + JS 页面                             |
|    │                                                                    |
|    └─ 第二步：通过 WebSocket 协议 (ws://192.168.1.100:8000/ws)          |
|               ──► 建立双向持久长连接，实时发送与接收聊天消息            |
+------------------------------------+------------------------------------+
                                     │
                     目标寻址：本机局域网 IP (192.168.1.100) + 端口 (8000)
                                     │
                                     ▼
+-------------------------------------------------------------------------+
| 服务器层：运行聊天室后端的电脑                                           |
|  ├─ 网卡接口 1：回环接口 `127.0.0.1` (仅供服务器本机自测访问)            |
|  ├─ 网卡接口 2：Wi-Fi 局域网接口 `192.168.1.100` (供同网络其他设备访问)  |
|  └─ [FastAPI 服务器进程]                                                |
|       └─ 启动时绑定 `--host 0.0.0.0 --port 8000` (同时监听上述所有接口) |
+-------------------------------------------------------------------------+
```

### 3. AI 给出的三个检查理解问题（附本组解答）

* **问题 1：如果服务器电脑的局域网 IP 是 `192.168.1.100`，但启动服务时执行的是默认命令 `uvicorn main:app --port 8000`（未加 `--host 0.0.0.0`），同局域网的小红用手机访问 `http://192.168.1.100:8000` 能连上吗？为什么？**
  * **本组解答**：不能连上。因为 Uvicorn 不指定 `--host` 时默认只绑定在 `127.0.0.1`（本机回环接口），只接收服务器本机自己发出的请求，直接拒绝来自 Wi-Fi 局域网网卡（`192.168.1.100`）的外部设备连接。
* **问题 2：为什么打开聊天室网页时先用了一次 HTTP，之后聊天却要换成 WebSocket？只用 HTTP 行不行？**
  * **本组解答**：打开网页是“浏览器主动向服务器要一份静态页面文件”，用一问一答的 HTTP 最合适；但多人聊天时，小明何时发消息是未知的，小红的浏览器需要被服务器“随时主动推送”。如果只用普通 HTTP，服务器无法主动向小红推送数据，小红只能不断手动刷新页面或让脚本每秒疯狂发请求轮询，既低效又有延迟；换成 WebSocket 后，双方保持一条常开的双向通道，消息一到就能毫秒级推送到小红页面。
* **问题 3：如果前端 HTML 代码里写死了 `new WebSocket("ws://127.0.0.1:8000/ws")`，在服务器本机测试一切正常，为什么换到第二台电脑打开页面后就无法收发消息？**
  * **本组解答**：因为前端 JavaScript 是在**访问者的浏览器里**执行的。当第二台电脑打开网页并运行这行代码时，`127.0.0.1` 指的是“第二台电脑自己”，而第二台电脑上根本没有运行服务器进程，所以 WebSocket 握手直接报错 `ERR_CONNECTION_REFUSED`。正确做法是使用 `new WebSocket("ws://" + window.location.host + "/ws")`。

### 4. 最常见的三个误区

1. **把 `0.0.0.0` 当作浏览器访问网址发给队友**：`0.0.0.0` 只能写在服务器启动命令 `--host 0.0.0.0` 里表示“监听所有网卡”；队友在自己手机或电脑浏览器里必须输入服务器的具体局域网 IP（如 `http://192.168.1.100:8000`）。
2. **混淆 `127.0.0.1` 与局域网 IP 的作用范围**：在服务器本机用 `127.0.0.1:8000` 测通了，就以为局域网已经通了，忽略了前端硬编码 `127.0.0.1` 或系统防火墙拦截 `8000` 端口的问题。
3. **误以为 WebSocket 断开后服务器会自动从列表里删掉连接**：如果把连接对象放进了 Python 的 `list` 中，当某台设备直接关掉浏览器或断网时，如果不捕获 `WebSocketDisconnect` 或发送异常并主动执行 `remove()`，死连接会一直留在列表里，导致后续广播报错中断。

## 第三部分：本组自己的话总结（任务 1.3 要求产出）

### 1. 我们原来最容易混淆的两个概念
我们原来最容易混淆的是 **`127.0.0.1`、本机局域网 IP（如 `192.168.1.100`）和 `0.0.0.0` 这三个地址的区别**；其次是容易把 **HTTP 请求加载网页** 和 **WebSocket 建立实时通道** 混为一谈，误以为只要浏览器能打开网页，WebSocket 就一定自动连上了。

### 2. 我们现在怎样区分它们
* **对于三个 IP 地址，我们用“快递收发室”来区分**：
  * **`127.0.0.1` 是“给自己写的内部便签”**：不管哪台电脑访问 `127.0.0.1`，永远只找它自己，绝不会走出这台电脑的网卡。所以只有服务器本机自测能用，队友千万不能用它访问。
  * **本机局域网 IP（如 `192.168.1.100`）是“服务器在路由器大院里的门牌号”**：队友的电脑和手机同处一个 Wi-Fi/热点大院时，必须在浏览器地址栏输入这个门牌号，才能找到服务器。
  * **`0.0.0.0` 是“服务器开门营业时的规则”**：写在服务端启动参数里，代表“不管是从内部便签（`127.0.0.1`）来的，还是从大院大门（`192.168.1.100`）来的客人，我都接待”。
* **对于 HTTP 与 WebSocket，我们用“领对讲机”和“用对讲机通话”来区分**：
  * **HTTP** 就像去前台“领一台对讲机（下载 HTML 页面）”，领完这次请求就结束了；
  * **WebSocket** 则是打开页面后，按下对讲机开关建立的“常开无线电频道”，只要频道开着，任何人在频道里说话，服务器都会实时广播给频道里的所有人。

### 3. 一个仍未完全理解、留待后续深入验证的问题
* **问题**：当某个用户不是正常关闭网页，而是**手机突然断掉 Wi-Fi 或直接拔掉网线**时，服务器可能不会立刻收到正常的关闭握手信号（FIN/Close 帧）。在服务器尝试给这个“半死不活”的连接广播下一条消息之前，服务器到底要过多久才会发现它已经断线？如果在广播循环里其中一个连接突然抛出异常，怎样保证不会连累后面其他正常在线的用户收不到消息？
* **我们的初步验证思路**：在任务 1.6 的广播循环中，给每个连接的 `send_text()` 加上独立的 `try...except` 异常捕获，一旦发现某个连接发送失败，立刻将它标记为失效连接并从列表中剔除，同时继续给列表里剩下的正常连接发送消息（这一机制已在我们的 V1 代码中实装验证，并在第二周异常实验室中继续深入测试）。
